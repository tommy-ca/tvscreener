# Abstract DuckDB Filter Pipeline (Composition over Inheritance)

## Problem Statement

The initial plan suggests creating `MTFScanner` and `SQLScanner` possibly by inheriting from `BaseOpportunityScreener`. This creates an architecture mismatch, as the base screener is responsible for fetching, filtering, and scoring specific asset sets, whereas DuckDB SQL filtering is fundamentally a post-processing step on an already-fetched DataFrame.

## Findings

- `BaseOpportunityScreener` heavily relies on `_engine.rank_opportunities(df)`.
- If `MTFScanner` overrides fetching logic, it duplicates code. If it overrides ranking, it breaks the core logic.
- DuckDB's strength is that it can query the output of `_prepare_enriched_data()`.

## Proposed Solutions

### Option 1: Implement DuckDB as a Pipeline Step
1. Instead of creating isolated screeners, implement `DuckDBFilter(query: str, is_sql: bool)` that wraps or acts upon the DataFrame generated by an existing screener (e.g., `ForexScreener.get_opportunities()`).
2. Add a `.filter_sql(query)` or `.filter_mtf(expression)` method to `BaseOpportunityScreener` that applies the DuckDB engine *after* initial fetching and enrichment.

**Effort:** 2-3 hours
**Risk:** Low-Medium (prevents inheritance spaghetti and keeps code DRY).

## Acceptance Criteria

- [ ] DuckDB filtering does not duplicate `_fetch_all_data` logic.
- [ ] Any existing screener (Forex, Crypto) can seamlessly pipe its output into a DuckDB SQL filter.
